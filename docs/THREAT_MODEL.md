# Linx — Threat Model (STRIDE)

Version: Phase 0 (2026-09-23), installer, certd and step-ca rows updated in Phase 0b; API authentication rows updated in Phase 1 step 3 (2026-09-23); webhook, outbound, alert and `linx doctor` rows reviewed at the end of Phase 1A (2026-09-24, see "Phase 1A review" below); phone engine rows added at the end of Phase 1B (2026-09-24, see "Phase 1B review"); sign-in, browser phone line, relay, coturn and front door rows reviewed at the end of Phase 1C (2026-09-25, see "Phase 1C review"); trunk, numbering, outbound routing, WireGuard and firewall sync rows reviewed at the end of Phase 1D (2026-09-26, see "Phase 1D review"). This document is updated at the end of every phase.

## Assets
- Call and meeting media and signalling
- Recordings, voicemail and transcripts
- SIP secrets and trunk credentials
- Device private keys (these stay on the device)
- CA keys (offline root, online intermediate)
- DNS provider token
- APNs key
- Admin accounts
- API keys, OAuth client secrets, webhook signing secrets, alert channel tokens
- Database encryption key (`linx_db_encryption_key`)
- API token signing key (`linx_jwt_signing_key`)
- CDR and directory data (personal data)
- Toll balance: fraudulent calls cost real money

## Trust boundaries
1. **Internet ↔ edge** (proxy/SNI router, coturn UDP 443, trunk SIP)
2. **Edge ↔ `linx-public` services**
3. **`linx-public` ↔ `linx-private`** (DB, Valkey, step-ca, ARI/AMI)
4. **Server ↔ third parties** (APNs, ACME CAs, DNS provider API, SMTP, later Meta/Telegram)
5. **Device ↔ server** (enrolled device, guest browser, desk phone)
6. **Host ↔ containers** (Docker socket, container management UIs)

## STRIDE by component

| Component | Threat (STRIDE) | Mitigation | Phase |
|---|---|---|---|
| SIP registration (Asterisk WSS/TLS) | **S** credential brute force, registration scanning | No public 5060; SIP only over WSS/TLS; long random secrets that are never displayed; per-IP and per-user rate limit and lockout at the edge (control-plane auth on WSS upgrade), with a fail2ban-equivalent ban list | 1 |
| Outbound calling | **E**/financial toll fraud | International dialling off by default; per-extension concurrency and spend limits; premium numbers blocked; alerts | 1 |
| Trunks | **S** spoofed INVITEs from the internet | Registration trunks by default (dynamic IP); IP-auth trunks allowlisted; `sip.` restricted to allowlisted sources | 1 |
| Media | **I** eavesdropping | DTLS-SRTP mandatory for WebRTC; unencrypted RTP rejected except on ADR-023 trunks; E2EE for meetings by default | 1/3 |
| Unencrypted trunks (ADR-023) | **I**/**T** calls overheard or altered between Linx and the provider | Only after TLS/SRTP fails the wizard test; admin confirms a plain-language warning; shown as unencrypted in the trunk list and `linx doctor`; recommended fix is a WireGuard profile; IP-auth 5060 limited to provider addresses | 1 |
| WireGuard profiles (ADR-024) | **I**/**D** leaked private key; a VPN capturing or cutting all traffic | Keys are secrets, never re-displayed; split tunnel enforced (full-tunnel `AllowedIPs` narrowed to trunk addresses); only a dedicated service has `NET_ADMIN`; handshake health per profile | 1 |
| coturn | **E** relay abuse / SSRF into LAN | Every IPv4 and IPv6 address denied as a peer except Asterisk's exact `linx-media` address (1C: rendered at start from Asterisk's alias, re-checked every minute; `linx doctor` compares it with Asterisk's real address). Tested on the real image: relaying to another container, the relay itself, loopback, the Docker host, a LAN, the internet or multicast all get 403. `no-tcp-relay`; `linx-media` is internal with only coturn and Asterisk on it (doctor checks). HMAC credentials (1 h, secret `linx_turn_secret`); 10 allocations per person, 300 total, 64 kB/s each; non-root, no capabilities, read-only | 1 |
| Guest links | **S**/**E** forged or replayed tokens, PIN brute force | EdDSA JWT with pinned algorithm; `aud`=room; `exp`; revocation table; PIN attempt limits + backoff; lobby | 3 |
| Enrollment QR | **S** QR photographed and reused | 10-min, single-use `jti`; bound to one extension; CSR from the device key; QR carries no SIP secret; admin can revoke | 2 |
| Device certificates | **S** stolen device | Secure Enclave keys (non-exportable); 7-day lifetime; deny-list checked on connect and pushed to live sessions | 2 |
| Pinning | **D** CA change bricks clients | Pin root SPKIs of primary + fallback CA; pin-set updates over the authenticated channel before any change | 2 |
| Admin console | **S**/**E** account takeover | LAN/VPN only by default; OIDC or local + TOTP/WebAuthn; RBAC; audit log; optional proxy SSO (Pangolin) | 1 |
| REST API / webhooks | **T**/**R** forged webhooks, key leak | Hashed and scoped API keys; HMAC-signed outbound webhooks; replay-safe delivery log; audit | 1 |
| Outbound requests (webhooks, CRM, storage) | **I** SSRF | Private ranges blocked by default with an explicit allowlist; timeouts and size limits | 1 |
| Web app | **T**/**I** XSS/CSRF | Strict CSP (no inline scripts), HSTS, Secure/HttpOnly/SameSite cookies, CSRF tokens, output encoding; external content treated as untrusted | 1 |
| step-ca | **E** CA key compromise | Offline root: generated inside a network-less bootstrap container, written only encrypted with a generated passphrase that is shown once and never saved; the CA volume never holds the root key (tested). Intermediate key encrypted, its password a group-restricted Docker secret; CA only on `linx-private`; non-root, read-only container; no remote admin API | 0 |
| step-ca | **E** rogue certificate issuance | Separate provisioners: `linx-services` (24 h max) and `linx-devices` (7 d max), limits enforced by the CA (tested); the device provisioner's password is mounted only into the control plane; no SSH certificates | 0 |
| Root key backup | **I** encrypted backup left on the server | Owner told to copy `/etc/linx/ca-backup` off the server and delete it; folder root-only; `linx doctor` warns while it is still there | 0 |
| linx-certd | **I** DNS token leak → domain hijack | Least-privilege token (Cloudflare: `Zone:Read` + `DNS:Edit` on the one zone), stored as a Docker secret, never logged (tested); CAA records restrict issuance. Setup reads it without echo, never writes it to `setup.yaml` or `.env` (tested), and saves it root-owned, group 65532, mode 0440 in a root-only folder | 0 |
| Service images | **T** a re-pushed image tag runs different code | Setup pulls `sha-<commit>` tags matching the `linx` binary, from CI's cosign-signed builds. Open: tags aren't digest-pinned or signature-checked on the server yet; a release manifest with digests and a cosign check arrive with `linx upgrade` | 0 |
| linx-certd | **I** hostname discovery via CT logs | Wildcard certificate by default, so `sip.`/`turn.`/`admin.` never appear in public logs | 0 |
| linx-certd | **T**/**D** half-written or stolen certificate files | New versions written to a fresh directory, then an atomic symlink swap; key `0640` (shared group only); ACME account keys `0600` in a separate volume; non-root, read-only container, all capabilities dropped | 0 |
| DNS automation | **T** clobbering user records | 1C (built): only `meet.`/`api.`/`turn.` under Linx's own domain, never Cloudflare-proxied, a CNAME is never touched; records are tagged with the comment `Linx`, and the background IP follower changes only tagged ones (a hand-made record is reported and left alone, tested). `linx setup`'s one-off run may take a name over, since the owner just asked for it, and prints what it did. Preview before write comes with the Domain & DNS page | 1 |
| Push gateway | **S**/**D** push spam, APNs key leak | APNs key as a Docker secret; VoIP pushes only for real calls (Apple policy); push rate limits per device | 2 |
| Docker host | **E** container escape, socket abuse | Non-root containers, read-only FS, no-new-privileges, dropped capabilities, seccomp; the Docker socket is never mounted into Linx services; container UIs warned as root-equivalent and bound to LAN | 0 |
| Installer | **T** supply chain | Docker's apt signing key is embedded in the `linx` binary (fingerprint checked by tests), not downloaded; packages come only from Docker's official repo; images pinned by digest and cosign-verified; SBOM; CI blocks high/critical CVEs | 0 |
| Installer | **E** privilege | `linx setup` runs as root and shows every step before applying it (`--dry-run` shows the exact commands); Docker group membership only for the `linx` system account, which has no login shell | 0 |
| Container management UI (Portainer, optional) | **E** root-equivalent via the Docker socket | Off by default; bound to the private LAN address only (loopback + SSH tunnel if the server has none); generated admin password in a root-only file mounted as a secret; image pinned by digest; setup warns never to port-forward it (ADR-019) | 0 |
| Backups | **I** data exposure off-site | Client-side encryption (restic) with an owner-held passphrase; private keys excluded by default | 5 |
| Logs | **I** secret or personal data leakage | Structured logging with redaction of tokens/secrets; retention limits | 0+ |
| Presence/directory | **I** over-sharing | Server-side visibility filtering by RBAC scope; served only to authenticated devices | 1/4 |
| Session inactivity | **S** abandoned devices | 7-day expiry via certificate lifetime + token revocation; pushes stop | 2 |
| Public API (`api.`) | **S** stolen/guessed API key or client secret | 256-bit random secrets, stored only as SHA-256 and compared in constant time (an unknown id costs the same hash); `linx_`/`linxcs_` prefixes with gitleaks rules in CI (`.gitleaks.toml`); expiry (default 1 year, max 2); optional IP allowlist; instant revocation; 20 failed attempts/min per IP (IPv6 per /64), then 429, every failure audited. Revoked/expired is only revealed to a caller who proved the secret (ADR-027, built) | 1 |
| Public API | **E** key does more than intended | Each operation's scopes are declared in `api/openapi.yaml` and enforced by the validator before the handler (a test fails if a new operation forgets them); effective scopes = key scopes ∩ role ceiling, re-checked on every request; a new key/client can't exceed its creator's role or scopes (no minting a stronger key); sensitive scopes (recordings, transcripts, call control, key and client management) never granted by "all" | 1 |
| Public API | **T**/**D** malformed or huge requests | Spec validation before handlers, unknown fields rejected, 1 MiB body limit, per-key rate limits, problem+json errors without internals | 1 |
| Browser sessions (1C) | **S** CSRF / cookie theft / login CSRF | `__Host-` cookies, `HttpOnly; Secure; SameSite=Strict`, 256-bit random, stored as SHA-256; CSRF header checked against the session's own hash on every write. Sign-in and set-password links (which have no session yet) take only `application/json`, which another site can't send without asking (tested). Sessions: 30 days / 7 idle for people, 12 hours for admins; one waiting on its authenticator code lasts 15 minutes (tested) | 1 |
| People accounts and sign-in (1C) | **S** password guessing, MFA bypass, account takeover | Argon2id; 12+ characters, common passwords refused; unknown and disabled emails take as long as a wrong password. Per address: 20 failures a minute (shared with API keys). Per account: after 5 failures each try waits (1 min, doubling, up to 1 h), the right password included; the same budget covers authenticator codes; an alert after 20 tries in an hour, counting tries during the wait (tested on Postgres). MFA required for admins. Each authenticator code and recovery code works once (a later step than the last accepted, claimed in one conditional update; tested on Postgres), so a code seen over a shoulder or replayed from a captured request is refused. Every sign-in step is audited (who, from where, why refused; never what was typed). A session waiting on its authenticator code holds no scopes and can't enroll a new authenticator, confirm one, or change the password once the account has one (tested: this was open, see "Phase 1C review"). Changing or disabling a person, their role or their password ends all their sessions and their browser phone lines at once | 1 |
| Set-password links (1C) | **S**/**E** a link used twice, or used to take over an account | 256-bit, stored hashed, 24 h, claimed atomically (two racing uses can't both win, tested on Postgres); using one ends the person's other sessions and still asks for their authenticator code if they have one. An admin can't issue one for (or change, demote or disable) someone whose role they couldn't grant, i.e. a system admin (tested). Refused for a disabled person. The link is shown once, never in `Referer` (`no-referrer`) | 1 |
| OAuth tokens | **S** forged or replayed JWT | EdDSA only (alg pinned; `none`, HS256 alg-confusion and other keys refused, tested), `kid`, `iss`, `aud`, `exp`/`nbf`/`iat` all required, lifetime ≤ 15 min, `jti` revocation (ADR-012). The client is looked up on every call, so revoking it kills its live tokens at once; a token can only narrow the client's current scopes. Signing key is an installer-generated Docker secret | 1 |
| Rate limits / audit | **S**/**D** spoofed `X-Forwarded-For` to dodge limits or pass IP allowlists | Header only believed from `LINX_TRUSTED_PROXIES` (empty by default), right-most untrusted hop used; never believed at all when front doors send PROXY v2 (1C: they pass TLS through, so the header could only be the visitor's own, tested) | 1 |
| `linx api-key` | **E** creating keys without the API | Runs as root on the host via `docker exec` into the control plane; that is already root-equivalent (Docker), so it adds no new path; every key it makes is audited as `system:cli` | 1 |
| API writes | **R** "I didn't do that" | Append-only `audit_log` with actor, key/client id, IP, action, target, result | 1 |
| Webhooks / alert senders / later CRM | **I**/**E** SSRF into `linx-private`, the LAN or cloud metadata | `internal/safehttp` (built): HTTPS only with normal certificate checks; no redirects; no environment proxy; the host is resolved once, **every** address checked (one private answer refuses the lot), and the dial goes to a checked address, re-checked in the dialer's `Control` hook (no DNS-rebinding window). IPv4-mapped, NAT64 and 6to4 addresses are checked as the IPv4 they reach. Private, CGNAT, link-local, documentation and similar ranges are refused unless on the outbound allowlist; loopback, `0.0.0.0/8`, multicast, reserved, cloud metadata addresses and the container's own networks (read from its interfaces at start) are refused even then. The allowlist is read per connection and fails closed. URLs are also checked when saved, so the admin hears at once (ADR-028) | 1 |
| Outbound allowlist | **E** allowlist used to open up the server itself | Entries must lie inside one private range (no `0.0.0.0/0`, no public ranges, no loopback or metadata) or be an exact host name; `outbound_allowlist:write` is a sensitive scope (never in "all"); every change audited | 1 |
| Webhook "Test" | **I** response reading turns the test button into a fetch tool | Only to addresses the guard allows (public, or the admin's own allowlisted LAN hosts); only the first 4 KB is kept; needs `webhooks:write`; audited | 1 |
| Webhooks | **S** receiver fooled by fake or replayed events | Standard Webhooks HMAC-SHA256 over id + timestamp + body (tested against the reference vector); receivers told to reject old timestamps and de-duplicate ids; secret rotation with 24 h overlap (both signatures sent) | 1 |
| Webhooks | **T** event sent for a change that rolled back, or lost | Transactional outbox: the event row commits or rolls back with the change; workers claim with `FOR UPDATE SKIP LOCKED` and a 2-minute lease, so a crashed worker's delivery is retried (at-least-once) | 1 |
| Webhooks | **D** slow or hostile receiver ties up the server | 10 s total timeout, 64 KB response headers, 4 KB kept + 64 KB drained, 8 concurrent sends, retries spread with jitter; 410 or 5 days of failures turns the endpoint off and cancels its queue | 1 |
| Webhooks | **I** personal data in payloads | Only what each event needs; never recording/transcript contents; delivery log kept 30 days | 1 |
| Webhook secrets | **I** secret leaks from the API or logs | Shown once (create, rotate); stored sealed (AES-256-GCM bound to the endpoint row); never in list/get responses, audit details or log lines; URLs with a user name or password refused | 1 |
| Stored integration secrets | **I** database dump leaks tokens | AES-256-GCM with a key held as a Docker secret, bound to the row (ADR-030) | 1 |
| Admin alerts | **D** alert flood hides real problems | De-duplication by key, flap hold-back (5 min stable before the first send), reminders at most every 24 h, one digest after quiet hours (built: `internal/alert`) | 1 |
| Admin alerts | **D**/**T** a notice sent twice, or "fired" sent for a problem that already cleared | Each notice is claimed with a compare-and-set on the alert row (still open and never notified, etc.) in the same transaction that queues it, so a stale scan or a second control plane queues nothing (tested) | 1 |
| Admin alerts | **D** a problem getting worse goes unnoticed | A notified alert whose severity rises (e.g. certificate warning → critical) is re-sent on the next tick, not at the next 24 h reminder (tested) | 1 |
| Alert channel settings | **I** channel URLs/tokens leak (Slack/Teams URLs, Telegram bot tokens, ntfy access tokens) | Sealed as one JSON object per channel (AES-256-GCM, ADR-030), same as a webhook secret; never returned by the API once saved, only usable through Test | 1 |
| Alert channel URLs (ntfy/Gotify server, Slack/Teams/webhook URL) | **I**/**E** SSRF via an alert channel | Same `internal/safehttp` guard as webhooks: checked at save time and every send | 1 |
| Certificate renewal alert source | **T** control plane trusts a spoofed `/metrics` response | Fixed hostname (`certd`, compose service DNS) on `linx-private` only, not admin-configurable; if wrong, the worst case is a missed or spurious alert, not a security bypass. Warning under 21 days left, critical under 7 — the same thresholds as `linx doctor` | 1 |
| `linx doctor` | **I** the health check leaks secrets or changes data | Runs as root on the host only; reads the database with one read-only query through `docker exec psql` (local socket inside the Postgres container, no network credentials), secret files only by `stat` (size, owner, mode — never contents); open alerts shown by title and message, which never contain secrets | 1 |
| `linx doctor` | **R**/**D** a broken install looks healthy | Checks every container (the control plane now has a Docker health check, `service healthcheck`, since the image has no shell), the schema version, that an API key and an alert channel exist, every open alert (critical = problem, exit code 1), and that each secret file exists, has the right size, is root-owned and not world-readable | 1 |
| Phone engine image (Asterisk) | **T** tampered source or build | Built by Linx CI from the official release tarball: SHA-256 pinned, and its GPG signature checked against Sangoma's key with a pinned fingerprint; sound prompts pinned by SHA-256; the Opus codec (Wazo's, Phase 1C, ADR-041) pinned by commit and each file's SHA-256, with Linx's one patch in the repo; base images pinned by digest; Trivy and cosign like every Linx image. The bundled pjproject is downloaded by Asterisk's build and checked against a checksum inside the signed tarball (see residual risks) | 1 |
| Phone engine container | **E** a flaw in Asterisk becomes a foothold | Only the modules Linx uses (no chan_sip, AGI, AMI); non-root (uid 100), read-only root filesystem, all capabilities dropped, `no-new-privileges`, memory and process limits; nothing in it listens except 5061, the audio ports and (Phase 1C) the browser websocket, HTTPS only, on its internal `linx-sipws` address (plain HTTP off; `linx doctor` and the call suite check its sockets); its database login reads four views only; its ARI user is read-only | 1 |
| Device logins (SIP, LAN only in 1B) | **S** guessing or reusing a phone's login | 130-bit random passwords generated by Linx, shown once (`Cache-Control: no-store`) and never stored, only the digest hash; random usernames, so an extension number never reveals a login; one login per device, revoked on its own; `devices:write` is a sensitive scope (never in "all"). Requests from outside `LINX_SIP_NETWORKS` are refused before authentication (Asterisk ACL, 403, tested). No lockout yet: registration lockout is a precondition for going public (1C) | 1 |
| Phone ports | **I**/**S** SIP or audio reachable from the internet | Three layers (docs/PBX.md §2): published on the LAN address only; nftables table `inet linx` drops 5061 and the audio range from outside the LAN, and 5060 from everyone, before Docker's port forwarding; the Asterisk ACL. `linx doctor` checks all three and the `sip.` DNS record. Ruleset checked with real `nft` in network namespaces | 1 |
| SIP signalling | **I**/**T** eavesdropping or downgrade | TLS only (no UDP or TCP transport exists); TLS 1.2 minimum, 1.3 offered (OpenSSL `MinProtocol`; 1.0 and 1.1 refused, tested); the publicly trusted certificate from `linx-certd`, which doctor checks is the one being served | 1 |
| Media (1B) | **I** unencrypted audio | Every device requires SDES-SRTP (`media_encryption=sdes`, not optimistic): an offer without encryption is refused with 488 (tested). The SDES keys travel inside the TLS signalling. Web devices (1C) require DTLS-SRTP, checked against the certificate fingerprint in the signalling (`dtls_verify=fingerprint`). Asterisk stays in the audio path, so it decrypts and re-encrypts (a PBX-anchored call, as documented) | 1 |
| Caller ID | **S** a phone claims to be another extension | Caller ID comes from the device's realtime row (its extension's number and name), not from what the phone sends; the name is stripped of caller-ID syntax characters | 1 |
| Device revocation | **S**/**E** a lost phone comes back | Revoking a device, or deleting its extension, sets `revoked_at` for good: the API refuses to change or re-enable it (409 `device_revoked`) and a database check refuses it too (tested). Asterisk reads the database on every registration and call (no cache), so the revoked phone's next request fails (tested) | 1 |
| Realtime data (`linx_asterisk`) | **I**/**T** Asterisk reads or changes more than it needs | The role can `SELECT` four views in schema `asterisk` and nothing else (tested: permission denied on every table); it can't write anywhere; its password is a Docker secret, set by the control plane at every start, never in the schema | 1 |
| Digest hashes | **I** a database dump leaks phone logins | A device's `md5_cred` works like its password for SIP digest login on this server (it's bound to the username and realm, and the password is random, so it opens nothing else). Treat database dumps and backups as holding device logins; reset-password or revoke replaces one. Never in API responses, events or audit details | 1 |
| Dialplan | **T**/**E** dialled digits injected into dialplan or SQL | Only digit patterns reach the extension lookup, and `func_odbc` escapes its argument; device usernames match `^d_[A-Za-z0-9]{8}$` (database check), so nothing from the database can add Dial options. Since 1D, outside calls go through `linx-outbound`, whose line list comes from `asterisk.linx_outbound` filtered to trunk ids, digits and `+` (see "Outbound routing") | 1 |
| ARI (control plane ↔ Asterisk) | **S**/**I** a fake Asterisk or a fake control plane | Asterisk connects out over TLS to `linx-ari`, served on `linx-private` only, and checks the control plane's 24 h step-ca certificate and host name; it presents `linx_ari_password` (constant-time check); one connection at a time. REST over that websocket runs as a read-only ARI user, so the control plane can watch calls but not start, change or listen to them; AMI is off, and Asterisk's HTTP server serves only the browser websocket on `linx-sipws` (1C) | 1 |
| `/sip` relay (1C, internet → control plane → Asterisk) | **S**/**E**/**D** someone uses another person's line, guesses a line's password, or floods Asterisk | Needs a signed-in session cookie (not pending MFA) and `Origin` = `https://<Host>` (no cross-site websocket); relays only for the session's own web device: every request's `From` (and `To` on REGISTER, and any `Authorization` username) must be that exact username or the connection closes and is audited; method allowlist; 64 KB per message, 20 messages/s; 3 rejected authentications in a row close it. Lines are per session and exist in Asterisk's views only while the session is live, so signing out or disabling a person ends them on the next lookup, and the relay drops the connection at once (plus a 15 s re-check). Each browser frame must be exactly one SIP message: CRLF-only header lines and a body of exactly `Content-Length` bytes, so a second message or a header hidden behind a bare line feed can't slip past the checks (1C review, tested). Tested with a fake Asterisk (unit) and the real one (call suite). 5061 stays LAN-only: no unauthenticated SIP on the internet | 1 |
| Browser websocket (1C, control plane ↔ Asterisk) | **S**/**I** something else reaches Asterisk's websocket, or impersonates it | `linx-sipws` is an internal network with only the control plane and Asterisk on it; Asterisk listens on that address only (tested: unreachable from the phones' network) and its SIP ACL admits that network besides the LAN. The control plane checks Asterisk's 24 h step-ca certificate for `linx-sipws`; the control plane issues it and writes it to a memory-only volume Asterisk reads, so Asterisk never holds a CA credential. Devices still authenticate with their digest login. Who may use it (signed-in, session-bound, lockout) is the step 4 relay | 1 |
| Web client and HTTPS 8443 (1C step 5) | **T**/**I** script injection, framing, downgrade, leaking a set-password link | One origin for page, API, `/sip` and the Team websocket; certd's certificate only (plain HTTP just on the container's loopback, for the health check). Every response: CSP `default-src 'self'` with no inline scripts or styles and `connect-src 'self'`, `frame-ancestors 'none'` + `X-Frame-Options: DENY`, HSTS, `nosniff`, `Referrer-Policy: no-referrer` (a `/setup/<token>` path never leaves in a Referer), `Permissions-Policy` allowing only the microphone and speaker choice to this origin. React escapes all text; no `dangerouslySetInnerHTML`. The SIP password stays in the page's memory; only audio-device choices go in `localStorage`. The build pins every npm package (licence and audit checked in CI) | 1 |
| Team list and status (1C step 5) | **I** who's on a call is visible; **D** websocket floods | `GET /team` needs `team:read` (every role has it: the Team screen is for everyone signed in); the live websocket takes only a signed-in browser session from this origin, reads nothing from the page, closes when the session ends (30 s check), and sends one list per change (coalesced, 150 ms); at most 8 open per session (tested). Status is the person's own choice (`/me/presence`, session only); "Do not disturb" only stops their own extension ringing | 1 |
| Front door (1C step 6: Pangolin at home, Linx takes 443) | **S** someone fakes a visitor's address to dodge the sign-in lockout; **I**/**T** the front door reads or changes traffic | Front doors pass TLS through by name without decrypting (Linx's own certificate end to end, so Pangolin's policy of not checking backend certificates never applies), and send the visitor's address with PROXY protocol v2. On 8443 the header is required from `LINX_TRUSTED_PROXIES` and refused from anyone else (tested); names (`linx-sni`) are re-resolved, and a name that stops resolving is trusted at none of its old addresses. With Pangolin at home, 8443 and 5349 are published on the LAN address and the firewall admits only Pangolin's address (doctor checks). `linx-sni`: HAProxy LTS pinned by digest, TCP mode only, no certificates or secrets, non-root, read-only, no capabilities. DNS records are written only for `meet.`/`api.`/`turn.`, never Cloudflare-proxied, CNAMEs left alone | 1 |
| Front door (1C step 7: nginx/HAProxy, HTTP-only proxy, home only, IP follower) | **I**/**T** an HTTP-only proxy sees and could change traffic; **S** a forged X-Forwarded-For; **T** DNS records pointed elsewhere | nginx/HAProxy pass through like Pangolin. An HTTP-only proxy is the owner's own and decrypts by design; the generated settings make it check Linx's certificate for `meet.<domain>` (never skip-verify; tested with a real Caddy), and Linx believes X-Forwarded-For from its address only, taking the right-most untrusted entry (a PROXY header is refused from everyone in that mode). The IP follower writes only `meet.`/`api.`/`turn.` (never proxied) with the token certd already holds, from Cloudflare's own trace over HTTPS; it rejects a private or malformed answer | 1 |
| Call events | **I** personal data in call webhooks | Numbers, device id and name, outcome and durations only; never audio or content | 1 |

## Residual risks and open items
- Browser websocket (1C step 2, reviewed in step 8 and accepted): Asterisk doesn't tie a device's kind to its transport, so a softphone login could sign in over the websocket and a web login over 5061 from the LAN. Only the control plane can reach the websocket, and the relay allows only the signed-in session's own web device; a web login's password lives only in the browser's memory, and its endpoint demands DTLS media that a desk phone can't offer.
- API rate limits are per control-plane instance until a Valkey-backed limiter exists (single node now).
- Failed-auth limiting is per IP: an attacker behind the same NAT as a real user can hold that user off for about a minute. Accepted; the alternative (per-key lockout) lets anyone lock out a known key id.
- One token-signing key, no rotation yet. Losing or replacing `linx_jwt_signing_key` only ends access tokens early (they last 15 minutes), so it needs no backup. Rotation with two `kid`s arrives when needed.
- `token_revocation` is checked on every token but nothing writes to it yet (revoking a client already stops its tokens). It is used by guest and enrollment tokens later (ADR-012).
- Losing `linx_db_encryption_key` makes stored integration secrets unreadable; backups must hold it separately from the database dump.
- Webhook URLs are stored in plain text. A receiver that puts a token in the query string (rather than verifying the signature) has that token readable by anyone with `webhooks:read` or a database dump. Slack/Teams-style URLs for admin alerts are sealed (step 5).
- The outbound allowlist is server-wide. With multi-tenancy it must become `system_admin` only.
- LAN receivers need a certificate from a public CA (e.g. Let's Encrypt via their own reverse proxy); a custom CA per endpoint isn't supported yet.
- Idle outbound connections are reused for up to 30 s, so removing an allowlist entry can take that long to affect a receiver already connected.
- An endpoint turned off for failing only writes a log line and an audit entry until admin alerts arrive (step 5).
- Standard Webhooks receivers reject messages whose timestamp is more than ~5 minutes off, so the server's clock must be right (NTP).
- `Idempotency-Key` isn't implemented yet; no step-4 endpoint needs it (creating a webhook returns its secret, like API keys, so it isn't idempotent by design).
- Disk/storage-nearly-full and DDNS-update-failure alert sources (docs/API.md §5) are not wired up: the control plane container has no filesystem of its own to check (`read_only: true`, no volumes) and no host-disk or DDNS-updater signal reaches it without either a Docker socket mount (against the "no Docker socket mounts" rule) or a new host mount / DDNS-updater feature. Revisit when either is designed.
- The certificate renewal alert only reads `linx-certd`'s expiry and failure-count metrics; it can't tell a slow ACME provider from a broken DNS provider apart. The message points the admin at `linx doctor` and the certd logs rather than guessing further.
- Alert channels are server-wide, like the outbound allowlist; with multi-tenancy they'll need a tenant scope.
- A problem that clears and comes back more often than every 5 minutes never passes the flap hold-back, so it never alerts. The same holds for a phone line that drops and recovers more often than its 2-minute "line down" wait (1D): someone able to make a trunk flap could keep it quiet. `linx doctor` and the trunk's state still show it. Revisit with "flapping" as its own alert.
- An alert that fired while no channel existed reaches a channel added later only at its next 24 h reminder. `linx doctor` warns when no channel is turned on.
- Alert rows (open and resolved history) aren't pruned; they grow slowly (one row per problem occurrence). Add retention with backups.
- Phone engine: the control plane holds the `linx-services` provisioner password, so a compromised control plane can get 24 h certificates for any internal service name (not for public names, and not the CA's own). Accepted: it already holds the database and every other service secret. Asterisk proves itself to the control plane with `linx_ari_password` (HTTP Basic inside TLS), not a client certificate: Asterisk's websocket client could present one, but that would need a renewal loop inside the Asterisk container; revisit with Phase 2's device-certificate work. The ARI user Asterisk exposes over that websocket is read-only.
- Device online state comes only from Asterisk's sign-in and sign-out events (registrations over TLS are dropped the moment the phone's connection closes, which is what makes this reliable). A sign-out that happens while the control plane is down or reconnecting is missed until that device's next sign-in or sign-out, so `online` can be stale after a restart.
- Calls between extensions aren't limited per device (docs/PBX.md §3); Asterisk's PJSIP has no simple per-endpoint call limit. Outside calls, the ones that cost money, are limited to 2 at once per extension since 1D (dialplan group count), and each trunk has its own limit.
- Trunks (1D review, accepted): an IP-authenticated trunk is recognised by the address its calls come from. Other customers of the same provider (providers share their signalling addresses), or something on the LAN taking a LAN peer's address (the UCM6304), can send calls that Linx takes as that trunk's. They reach only that trunk's own DIDs, the same as dialling the number; nothing leads out.
- Trunks (ADR-045, accepted): Asterisk checks providers' certificates per transport, so a CA pinned for one trunk (say, the UCM6304's own) is trusted for every TLS trunk's name. Whoever holds that CA's key and sits on the path to another provider could pose as it. Pin a provider's own certificate rather than a CA where it can be done.
- Trunks (1D review, accepted): a trunk's address is whatever an admin with `trunks:write` gives. The connection test refuses Linx's own networks and the WireGuard agent refuses routing them into a tunnel, but the Asterisk config and the host firewall take the address as given: a trunk pointed at a Linx container's address would only confuse Linx's own traffic (browsers' calls taken as that trunk's), not reach anything new. The browser call suite runs its test provider on a Linx network, so filtering those networks out would need the harness changed first.
- Inbound calls from a trunk aren't refused when the trunk is at its call limit (outgoing calls count them, so they can't be exceeded the other way); the provider's own channel limit applies. Emergency calls skip every limit, so a phone could place many at once; each raises the admin alert.
- The plain trunk port (5062, ADR-023) isn't published by Compose, so an unencrypted IP-authenticated provider on the internet can't call in yet; outgoing calls and "Linx signs in" trunks work, and the firewall rules for it exist. Publish it (LAN address, like 5061) when the first such provider is needed.
- No registration lockout on 5061: repeated wrong passwords from the LAN aren't blocked. Accepted while phones are LAN-only and passwords are 130 random bits. Browsers' public SIP goes through the `/sip` relay, which has its own lockout (1C step 4); 5061 needs Asterisk-side lockout before it's ever public (docs/PBX.md §6).
- Front door (1C step 7, reviewed in step 8 and accepted): the IP follower believes Cloudflare's trace for the public address, fetched over HTTPS with normal certificate checks; forging it needs a certificate for 1.1.1.1, and even then browsers and phones would see a certificate that isn't Linx's. An HTTP-only proxy holds Linx's traffic in the clear by design; the owner chooses it, and setup says so.
- Front door (1C step 6, reviewed in step 8 and accepted): Linx trusts Pangolin's home-network address; anything else on the LAN that takes that address could send PROXY headers (it could only claim other visitors' addresses, for the lockout, and still needs a valid sign-in). coturn behind a pass-through sees only the front door's address, so its quotas are per credential, not per visitor address (as designed).
- `/sip` relay (1C step 4, reviewed in step 8 and accepted): the 3-failure lockout is per connection; a signed-in person can reconnect and try again. Each try needs a valid session (itself behind sign-in lockout) and only ever reaches that session's own line, whose password is 130 random bits, so this only lets someone who is already signed in fail to sign in as themselves.
- Per-account sign-in lockout (1C): anyone who knows a person's email can make them wait (up to an hour between tries) by failing on purpose, and the lockout's "try again after" answer (which an unknown email never gets) shows that the email has an account. Accepted: the standard trade-off against guessing, the wait is capped, and the "someone is guessing a password" alert tells the admin. Revisit with company sign-in (1E).
- First-run authenticator enrollment (1C): until a new admin has scanned their authenticator app, whoever holds their set-password link or password can enroll their own instead. Links are shown once to the admin who made them and last 24 hours; the new person should use theirs promptly.
- Lost authenticator (1C): only a recovery code gets a person with MFA back in; a set-password link resets the password but never the authenticator. An admin "reset authenticator" (audited, ends sessions) comes with the admin portal (1E). Turning MFA off isn't possible at all yet.
- A signed-in session can start a new authenticator enrollment without re-entering the password (it still needs a code from the new app to confirm). Re-authentication for sensitive account changes comes with the admin portal (1E).
- Revoking a device (or ending a browser line's session: signing out from elsewhere, disabling the person) stops every new registration and call at once and it can no longer be rung, but a call already in progress on it continues until someone hangs up (the control plane's ARI user is read-only), and Asterisk keeps its old registration entry until it expires.
- Asterisk's build downloads its bundled pjproject (the SIP stack) and checks it against an MD5 checksum shipped inside the GPG-verified Asterisk tarball. MD5 is weak against collisions, not against a stranger forging a matching file; pinning pjproject's SHA-256 in the Dockerfile as well would close even that. Do it with the next Asterisk update.
- For TLS 1.2, Asterisk accepts OpenSSL's default cipher list at security level 2, which still includes some older (CBC) suites that desk phones may need. Tighten when the supported desk phone list is known (Phase 2 provisioning).
- Connections to Postgres on `linx-private` (control plane and Asterisk) aren't encrypted. The network is internal to the host (`internal: true`), so only something already on the server could read them. Revisit with multi-node deployments.
- The realtime views and the dialplan aren't tenant-aware (extension numbers are unique per tenant only). Fine with one tenant; multi-tenancy needs a context per tenant.
- Nothing creates the `sip.<domain>` DNS record yet: setup prints it and `linx doctor` checks it. The Domain & DNS automation (Phase 1) should add it.
- Asterisk and coturn can't see real client IPs on passthrough profiles. This is mitigated by pushing clients through WSS (where the control plane sees the IP) and by credential quotas on TURN.
- Server-decrypted call types (PBX-anchored calls, recordings, trunks) are documented honestly in the user guide.
- Dynamic IP with IP-auth trunks is unsupported (the wizard warns about this).
- CAA records aren't created automatically yet. Until the Domain & DNS page does it (Phase 1), the owner adds `CAA 0 issue "letsencrypt.org"` and `CAA 0 issue "sectigo.com"` (ZeroSSL) by hand.
- The device provisioner is protected by its password (a Docker secret for the control plane only), not by mTLS as first planned (accepted by the owner, 2026-09-23). step-ca has no per-provisioner client-certificate gate; revisit with an X5C provisioner in Phase 2 if needed.
- If the CA secrets in `/etc/linx/secrets` are lost, step-ca can't unlock its intermediate key. Rebuilding needs the root backup and passphrase (`docs/ops/INTERNAL_CA.md`).

## Phase 1A review (2026-09-24)
Security review of the API foundation (docs/API.md §8 steps 1–5): authentication, webhooks, the SSRF guard, admin alerts, the database access code and the installer's secrets.

**Checked and sound:** API keys and OAuth client secrets are 256-bit, stored as SHA-256 and compared in constant time, with unknown ids costing the same; revoked/expired/IP reasons are only told to a caller who proved the secret; JWTs are EdDSA-only with a pinned `kid` and every time claim required; OAuth clients are looked up on every call and tokens can only narrow the client's current scopes; the token's tenant must match the client's; `X-Forwarded-For` is only believed from configured proxies; every write and failed authentication is audited without blocking the response; every operation's scopes come from `api/openapi.yaml` and a test fails if one is missing; unknown JSON fields are refused. SQL is parameterised everywhere; the only table name built into SQL comes from a two-value whitelist. No log line prints a secret. The SSRF guard resolves once, checks every address (IPv4-mapped, NAT64 and 6to4 unwrapped) and dials only checked addresses; Linx's own networks, loopback and metadata can't be allowlisted. Webhook and alert channel secrets are sealed and bound to their row.

**Found and fixed in this review:**
1. The certificate alert fired at 14 days left, not the 21 (warning) / 7 (critical) days `linx doctor` uses and documents. Now the same.
2. Alert notices weren't claimed atomically: an alert resolved between the engine's scan and its fan-out would send "fired" and then "resolved" for a problem the flap hold-back should have absorbed, and two control planes would both send. Now a compare-and-set claim (see the Admin alerts rows).
3. An alert escalating from warning to critical waited up to 24 h to be re-sent. Now re-sent on the next tick.
4. Alert channel settings had no length limits in the spec (only the 1 MiB body limit). Now 2048 for URLs, 512 for tokens, 64 for topics and chat ids.
5. `linx doctor` couldn't tell whether the control plane was answering (no health check, no shell in the image). Added `service healthcheck` and a Compose health check, plus the doctor checks in the rows above.

**Still open (accepted for now, listed above):** per-instance rate limits; no `Idempotency-Key`; webhook URLs stored in plain text; LAN receivers need a public CA certificate; disk/DDNS alert sources; alert flapping; server-wide allowlist and channels; portal sessions not built yet.

## Phase 1B review (2026-09-24)
Security review of the phone engine (docs/PBX.md §8 steps 1–5): the Asterisk image and its rendered configuration, the realtime views and `linx_asterisk` role, device logins and the `/extensions`, `/devices` and `/calls/active` API, the ARI link and its step-ca certificate, the installer's phone ports and firewall, and doctor's phone checks.

**Checked and sound:** the Asterisk tarball's checksum and signature are both verified at build time against pinned values; the image runs non-root on a read-only filesystem with no AMI, no HTTP server and no AGI. Secrets rendered into Asterisk's config are refused if they contain a config-breaking character. `linx_asterisk` can read four views and nothing else. Device passwords are 130 random bits, shown once, stored only as the digest hash, and never appear in events or audit details. Every extension and device query is tenant-scoped; every write fires its event and audit entry in the same transaction. Caller ID is set by Linx, not the phone. The dialplan only passes digits to its one SQL lookup, and that lookup is escaped. ARI is TLS-only on `linx-private`, both sides authenticated, and read-only. The firewall only drops (never opens), runs before Docker's forwarding, and fails closed for IPv6 and for a server without a LAN; with Docker's `userland-proxy` left on, every phone would appear to come from Docker's own address, which the ACL refuses (fails closed too).

**Found and fixed in this review:**
1. Revoking a device only turned it off: `PATCH {"enabled": true}` brought it back with its old password, so a lost phone could sign in again. Now revocation is permanent (`revoked_at`, migration 0008, with a database check); a revoked device can't be changed, re-enabled or given a new password (409 `device_revoked`). Existing revoked devices are backfilled from deleted extensions and the audit log.
2. The phone TLS port accepted exactly TLS 1.2 and refused 1.3 (PJSIP's `method=tlsv1_2` means "only 1.2", checked against the image). Now `method=sslv23` with OpenSSL's `MinProtocol = TLSv1.2`: 1.2 and 1.3 accepted, 1.0 and 1.1 refused, checked in the call suite. The same floor applies to Asterisk's ARI connection.
3. Nothing tested that a phone offering unencrypted audio is refused. The call suite now checks it (488).
4. Asterisk named its exact version in every SIP response (`User-Agent`/`Server`). It now says `Linx`.
5. API responses carrying one-time secrets (device logins, API keys, webhook secrets) had no `Cache-Control`. Every API response is now `no-store`.
6. docs/PBX.md said the 200 audio ports carry 100 calls. Each phone's side of a call uses two ports, so it's about 50 calls between two phones (100 echo tests). Corrected; enough for home and small office.

**Found during the demo run (after the review):**
7. Asterisk couldn't start again after a restart (including a server reboot): Docker recreates a restarted container's tmpfs mounts as root-owned 0755, so the non-root entrypoint couldn't write `/etc/asterisk`. Fixed with explicit owner and mode on the mounts in compose.yaml and the directories created in the image; the call suite now restarts Asterisk and makes a call.
8. Asterisk named itself by its container address (e.g. `172.21.0.3`) in the From header of calls and checks it sent to phones; calling back from Linphone's history dialled that address. Now `from_domain` is `sip.<domain>` (migration 0010), checked in the call suite. Also found: Codec order (Opus first) silenced Linx's spoken messages; now G.722 first (migration 0009).
9. A renewed public certificate only reached Asterisk when it restarted. Fixed after the demo: the entrypoint reloads it within a minute of certd's swap, without dropping calls (docs/ops/CERT_RELOAD.md; call suite). `linx doctor` still checks the served certificate, and now skips Asterisk's console while it's starting instead of waiting on it.

**Still open (accepted for now, listed above):** no registration lockout (precondition for public SIP); per-device call limit; a call in progress on a revoked device continues; pjproject's checksum is MD5; TLS 1.2 cipher list; unencrypted Postgres on the internal network; not tenant-aware; `sip.` DNS record created by hand; Asterisk authenticates to the control plane by password, not certificate.

## Phase 1C review (2026-09-25)
Security review of the web client slice (docs/WEB.md §8 steps 2–7): people accounts and sign-in, sessions and CSRF, set-password links, the browser phone line and `/sip` relay, TURN credentials and coturn, the web client and its headers, the Team list, the front doors (PROXY protocol, trusted proxies, generated configs), DNS records and the IP follower.

**Checked and sound:** passwords are Argon2id and a wrong email costs the same as a wrong password; session, CSRF, setup-link and recovery-code secrets are 256-bit and stored hashed; every write through a cookie needs the CSRF header; a pending session holds no scopes, and the phone line, relay, TURN credentials and Team list all refuse it. A browser's phone line exists in Asterisk only while its session is live (the database view decides, whatever the control plane is doing), and the relay only relays that line's own username, byte for byte. coturn can relay only to Asterisk's exact media address; its credentials last an hour. The web page allows scripts, styles and connections from its own origin only, can't be framed, and sends no referrer; React escapes everything and nothing uses raw HTML; the phone line's password stays in memory. Front doors pass TLS through (Linx's certificate end to end) and must send PROXY v2 from a trusted address, which nobody else may send. The DuckDNS token never reaches a log (its URL is dropped from errors).

**Found and fixed in this review:**
1. **Authenticator bypass (serious).** Someone who knew only a person's password could sign in, get a session waiting on the authenticator code, and from it start and confirm a *new* authenticator app, which replaced the person's own and completed the sign-in without their code. It worked for admins too. A waiting session can now only enroll when the account has no authenticator yet (first run), and can't change the password (tested).
2. **Admins could take over a system admin.** An admin could issue a set-password link for a system admin (their password, then their session), or demote or disable one. Now an admin can only act on people whose role they could grant (tested).
3. **A set-password link skipped the authenticator code** for a person who had one (only admins were asked for it), and left their other sessions signed in. Now a link ends their other sessions and still asks for the code (tested). Links are also claimed atomically: two requests racing with one link could both set a password (tested on Postgres).
4. **The relay checked only the first SIP message in a websocket frame, and split headers on CRLF only.** Asterisk's SIP stack may read a second message after the body, or treat a bare line feed as a line break, so a crafted frame could carry a request (say, another line's username) the relay never checked. Now every frame must be exactly one message with CRLF-only headers and a body of exactly `Content-Length` bytes, or the connection closes and is audited (tested).
5. **Login CSRF.** Sign-in and set-password links took any content type, so another site could post a form that signed a visitor's browser in to an account of the attacker's choosing. Now JSON only (415 otherwise, tested).
6. **`X-Forwarded-For` was still believed on PROXY v2 front doors** when a connection showed the door's own address (a PROXY "LOCAL" header), letting a visitor pick the address the sign-in lockout counts. Now it's never believed when front doors use PROXY v2 (tested).
7. A session waiting on its authenticator code lasted as long as a full one (12 hours for an admin). Now 15 minutes (tested).
8. A wrong current password on `POST /me/password` wasn't counted anywhere. Now it draws on the per-address failure budget.
9. The Team list's websocket had no limit per session. Now 8 (tested).
10. The IP follower rewrote any `A` record for `meet.`/`api.`/`turn.`, including one the owner had typed in by hand, every 6 hours. It now changes only records Linx tagged (tested).
11. **The "someone is guessing a password" alert could never fire.** It needed 20 counted failures in an hour, but the lockout waits (1, 2, 4, 8, 16 minutes…) allow only about 10, and tries during a wait weren't counted. Now they count toward the alert without lengthening the wait (tested, also on Postgres).

**Still open (accepted for now, listed above):** per-account lockout can be used to make someone wait, and reveals that an email has an account; first-run enrollment trusts whoever has the link first; no admin authenticator reset or MFA off; no re-authentication for account changes; relay lockout per connection; transport not tied to device kind; the IP follower trusts Cloudflare's trace; HTTP-only proxies decrypt by design; Pangolin's LAN address is trusted; coturn quotas per credential, not per visitor.

## Phase 1D review (2026-09-26)
Security review of the phone-lines slice (docs/TRUNKS.md §13 steps 1–6): numbering and the outbound decision in SQL, trunks' data, API and CLI, the rendered Asterisk config and dialplan, the connection test, trunk state and alerts, the WireGuard agent, and the host firewall sync.

**Checked and sound:** a call from a trunk lands in a context that reaches only that trunk's DIDs, and every path from it avoids `linx-outbound` (unit-tested by walking the dialplan); a phone transferring an outside caller elsewhere hands the dialplan the trunk's channel, which the SQL decision treats as an unknown caller (emergency only). The outbound decision runs in `SECURITY DEFINER` functions with a fixed `search_path`, `linx_asterisk` can only execute them, and their line lists are checked in SQL to hold only trunk ids, digits and `+`, so no dialled number reaches `Dial()` unchecked; everything the dialplan passes to SQL goes through `SQL_ESC`. Extensions without a permission level fail closed. Numbers are classified from digits only (anything else is invalid), so provider feature codes (`*72…`) can't be dialled out. Provider caller names and numbers are filtered twice. Trunks are recognised by address, never by a From header, and don't challenge. Certificate checking is never off: the connection test uses the same trust (public CAs plus the pin, name always checked), resolves once, refuses Linx's own networks and dials only the checked address. Provider passwords and WireGuard keys are sealed, bound to their row, rendered only into memory-only volumes with tight modes, never returned or logged; the CLI reads passwords without echo or from stdin, never from a flag. The WireGuard agent refuses to route Asterisk's own networks into a tunnel and drops to a non-root user with only `NET_ADMIN`. The firewall sync touches only two fixed sets' elements, never a rule.

**Found and fixed in this review:**
1. **`extensions:write` could give an extension any call permission level**, including one that allows international or premium calls. `extensions:write` isn't sensitive (it's in "all"), while the design makes whatever decides costly calls need `routing:write` (ADR-048). Choosing or clearing a level now needs `routing:write` too (403 `scope_missing`, tested); the level is also in the create audit entry now.
2. **An ADR-023 confirmation outlived the change it covered.** Once an unencrypted trunk was confirmed, it could be pointed at another address or made less encrypted (TLS without SRTP → plain UDP) without the warning again. Now another host, transport or audio encryption on an unencrypted trunk asks again (tested).
3. **Trunks accepted transfer requests (REFER) from the provider.** The dialplan already sent such a transfer nowhere (the phone's side would land in `linx-from-trunk` with a phone's channel, which matches no DID), but nothing needs it: trunk endpoints now have `allow_transfer=no`.
4. **A DNS hiccup shut an IP-authenticated provider out of the host firewall.** The sync withdrew the address of any trunk whose name didn't resolve that minute, while Asterisk kept the last one. Now the control plane says `keep` and the sync adds but withdraws nothing that round (tested).
5. Changing a trunk's password, pinned certificate or WireGuard tunnel, and confirming it unencrypted, weren't in the audit entry's details. Now they are ("changed" for the password and pin, never their values).
6. docs/TRUNKS.md §12 said unencrypted IP-authenticated trunks use 5060. They use 5062 (5060 is never used); corrected, and the unpublished 5062 is listed above.
7. **The step 6 browser suite had failed in CI** (reported green by mistake): its API key lacked `routing:write`, which creating a call permission level already needed, so the Phase 1 exit test never ran. The key now has it; with fix 1, extensions that name a level need it too.

**Still open (accepted for now, listed above):** calls from shared provider addresses are taken as that trunk's (DIDs only); a pinned CA vouches for every TLS trunk; trunk addresses aren't screened against Linx's own networks outside the test and the WireGuard agent; inbound calls aren't refused at a trunk's limit and emergency calls skip every limit; a flapping line can stay quiet; 5062 isn't published; calls between extensions aren't limited per device.
