# Linx — Backup and restore

*Status: design drafted 2026-09-27, pulled forward from Phase 5 (`docs/ROADMAP.md`) at the owner's request, ahead of going live. ADR-055 records the owner decisions below. Steps 1–6 built; demo (`docs/DEMO_BACKUP.md`) not yet run.*

Two things: getting a working copy of Linx off the server regularly (**backup**), and getting a whole system back after loss — a dead disk, a destroyed VPS, a mistake — onto a fresh one (**restore**). `docs/ARCHITECTURE.md` already lists `backup`/`restore` as `linx` CLI subcommands; this is their design.

## 1. In plain words

- **What's backed up:** everything needed to bring Linx back exactly as it was — every person, extension, phone line, setting and the activity log — plus the keys that protect it. Nothing about your calls' audio; there isn't any stored.
- **Where it goes:** on the server itself, on another machine or storage service you point it at, or straight to your own computer as a single file you download from the admin portal. All three at once is fine — the schedule can push to more than one place.
- **On a schedule, or by hand:** turn on daily, weekly or monthly backups at a time you choose, or turn them off. "Back up now" always works too, from System → Backups.
- **Always encrypted, always asked for before anything sensitive:** the backup file is useless without its password, which Linx generates and shows you once — the same "you won't see this again" box as a device's login. Setting up where backups go, or downloading one, needs "confirm it's you" (ADR-053) first.
- **Getting back onto a new server:** run `linx setup` on the new machine as usual (domain, DNS, the Linx stack) — that part can't come from a backup, since it's how the new machine reaches the internet at all. Once it's up, the browser's setup wizard offers **"Restore from a backup"** as well as "Start fresh". Say where the backup is and give its password; the server does the rest and Linx restarts as it was (§4). Nothing to type over SSH, unless the backup is on a network drive or cloud storage, which is set up on the new server first with the same details as before.

## 2. What's in a backup

Two files, always made together and always used together — mixing an encryption-keys file from one backup with a database file from another silently breaks every stored secret (recovery codes, webhook secrets, everything sealed with ADR-030's key), so restore refuses to proceed unless their pair-id matches:

1. **The database** — a `pg_dump` of the whole Postgres database (control plane's own tables and the `asterisk` realtime schema): people, extensions, devices (only their digest hashes, never a password), phone lines (same), settings, the audit log, alert history. Sealed secrets (webhook signing secrets, TOTP secrets) are in here still encrypted with ADR-030's key — this file alone, on its own, doesn't reveal them.
2. **The keys** — the small set of Docker secrets a restored system can't regenerate and still be the same system: `linx_db_encryption_key` (ADR-030 — without it every sealed secret in the database file is unrecoverable garbage), `linx_jwt_signing_key` (ADR-027 — without it, every previously-issued API key and OAuth access token stops verifying). Kept in its own encrypted file, same as the database file, so a copy of just the database on its own never exposes them.

Both are wrapped into one [restic](https://restic.net) (BSD-2-Clause) repository, one snapshot per backup: restic already does exactly what this needs — content-addressed encryption (ChaCha20-Poly1305/AES-256, your repository password only, nothing readable without it), deduplication (so daily backups of a mostly-unchanged database cost little extra space or transfer), and back ends for a local path, SFTP and any S3-compatible service (AWS S3, Backblaze B2, MinIO, Cloudflare R2, …) without Linx writing its own upload code or its own crypto for this. It's a single static binary; `linx setup`'s prerequisites step gets it the same way it already handles Docker (download, checksum-verified, pinned version).

**Not included, on purpose:** call audio (never stored to begin with), TLS certificates (they renew themselves inside 90 days; a restored system gets fresh ones), the step-ca root key (ADR "Root... exported encrypted for offline backup" already covers it separately — that key protects every device's own certificate too, and deserves to live apart from a routine backup an admin might store somewhere more casually).

## 3. Where it goes (owner decision — restic backend, ADR-055)

One repository, one or more of:
- **Local** — a path on the server's own disk (a second drive is worth pointing this at; the same disk as Postgres isn't real protection).
- **Remote** — SFTP (any server or NAS you can SSH to) or an S3-compatible bucket (access key, secret, bucket, region/endpoint — restic's own flags, entered once and sealed the same way a webhook secret is).
- **Download** — System → Backups → "Make a backup file" backs up now and gives the admin who asked one `.tar` file of the backups kept on the server: the local repository's own files, **still encrypted** (never a decrypted dump), so it needs the same password as the folder it came from, which the same page shows on request (§6). Useful for a copy on your own computer without setting up remote storage at all; the setup wizard's "A backup file on my computer" takes it back (§8 step 5 "As built").

More than one destination just means more than one restic repository configured; the schedule runs the backup once and pushes the resulting snapshot to each.

## 4. Restore (owner decision — web setup wizard, ADR-055)

Restoring puts back *everything*: every person, every session ended, every setting overwritten. It has to happen before there's a normal admin session to protect — which is exactly the state the web setup wizard already runs in (docs/ADMIN.md §4), so that's where it lives, as its first screen for a system admin on a fresh install: **"Set up fresh" or "Restore from a backup"**.

*As built (step 4, owner decision 2026-09-27: "the browser asks, the server does it").* The first draft split restore in two (the keys by a command over SSH, the database from the browser, restored by the control plane itself). Step 3 settled that only host programs ever touch a backup — the control plane never has restic, a repository or its files — so the owner chose a third way: **the browser asks and the server's backup helper does all of it, keys and database together.** One step, all in the browser:

1. The wizard's restore screen asks where the backup is (a folder on this server — `/var/backups/linx` by default — or a destination set up here with `linx backup destination add`, for a NAS or cloud storage: its credentials don't travel with a backup, §7), which backup (the newest, or an id), and its password, and has the admin tick "I understand, replace everything". "Confirm it's you" (ADR-053) first; only a system admin's own session; only while setup isn't finished (`restore_after_setup` otherwise — `sudo linx restore` on the server works any time). `POST /backup-restore` stores the request with the password sealed (ADR-030's key, row `backup_restore:<id>`, table `backup_restore_request`, migration 0025).
2. `linx-backup-agent` (now every minute, not five) sees `run restore` from `backup pending`, takes the request (`backup restore-take`: marks it running and deletes the sealed password in the same statement, so it's in the database for about a minute at most), checks the location again on the host, and runs `linx restore --yes --json --password-stdin (--path F | --destination N) SNAPSHOT` (the password on stdin, never an argument).
3. `linx restore` (host, root; replaces step 1's `linx restore-secrets`): looks the snapshot up (resolving "latest" to its id), unpacks its dump and keys into a private folder under `/var/lib/linx`, loads the dump into a database of its own (`linx_restore`, `pg_restore --single-transaction --exit-on-error`), refuses a backup from a newer Linx (its `schema_migrations` newer than the live one's), ends every sign-in session in it and drops any backup/restore request it holds. **Nothing on the server has changed until here**; a failure so far leaves it exactly as it was. Then: stops the control plane, writes the two keys in place (the old ones kept as `*.before-restore`), swaps the databases by renaming (live → `linx_before_restore`, closed to new connections and its connections ended first; `linx_restore` → `linx`), starts the control plane, restarts Asterisk and waits for the control plane's health check. A failed swap puts the keys and database back and starts the control plane again. Afterwards the password that worked is saved for that destination (or the default local one), so later backups carry on in the same repository.
4. The keys and database always come from the same snapshot, so the pair id can't mismatch any more; `FindSnapshot` still refuses a snapshot without one (not a Linx backup).
5. The agent reports back: a failure to the request (`backup restore-failed`), which the wizard shows ("Nothing on this server was changed" — a restore that got further replaced the request along with the database); a success to the restored database's audit log (`backup restore-done` → `backup.restored`). The wizard polls `GET /backup-restore` every 3 seconds: waiting → restoring → (Linx restarting, network errors) → **401**, since the restored database has no session for this browser: "Restored — sign in with your accounts from the backup".

A request that's been running more than 45 minutes shows as failed (the agent's own limit is 30), and a new one can be made.

## 5. Schedule (owner decision, 2026-09-27)

Off by default. When on: **daily, weekly or monthly**, a time of day the admin sets (weekly also picks a day of week, monthly a day of month), each destination configured tried in turn with the others still attempted if one fails. Keeps the last 14 daily / 8 weekly / 6 monthly snapshots per repository by default (restic's own `forget --prune`, run right after each backup) — changeable later, not exposed as its own setting yet. A failed scheduled backup fires the existing "backup failure" alert (already in the catalog, `docs/API.md` §2, unused until now).

## 6. "Confirm it's you" and the repository password (owner decision, 2026-09-27)

The repository password is generated by Linx (like a device's SIP password, ADR-033) — never typed in by an admin, never weak, never reused between repositories — and shown exactly once, in a "you won't see this again" box, when a destination is first set up. *(As built, step 5: the browser shows it again only as "the backup file's password", to the admin who made that file, after a fresh "confirm it's you", audited each time.)* Every action that would show it again, add a new destination, or produce a downloadable backup needs a fresh "confirm it's you" (ADR-053) first: these are exactly as sensitive as a device's login or an API key, for the same reason (whoever holds the password holds the whole system).

## 7. Security

- Restic's own encryption is the only thing that ever protects a backup at rest; Linx doesn't add or substitute its own on top (one well-reviewed scheme, not two).
- A remote destination's own credentials (SFTP private key, S3 access key) are host-side secrets, exactly like a Docker secret: root-only files under `/etc/linx/secrets/linx-backup/`, one per destination, never in the database and never inside the backup itself. This is a deliberate change from this document's first draft, made in step 2 (below): `linx backup` is a host binary with no database connection of its own (it reaches Postgres only by shelling into `docker exec ... pg_dump`, the same as every other host-level Linx command), so there is nowhere in-process to seal a credential with ADR-030's key the way a trunk's or webhook's secret is. One consequence worth being explicit about: **a remote destination has to be reconfigured by hand after a disaster-recovery restore onto a new server** (its credentials don't travel with the backup) — treated as the safer default, not just an implementation shortcut, since it also means one destination's snapshot never contains another destination's own keys.
- Outbound connections to a remote destination go through the same host-safety check every other admin-supplied address gets (`backup.CheckDestinationHost`, reusing `internal/trunkprobe.RefuseOwn`): loopback/unspecified/multicast/link-local and Linx's own container networks are refused, an ordinary private LAN address (a home NAS) is allowed.
- `linx restore` is destructive (it replaces the database and the keys); it refuses to run without an explicit `--yes`, keeps what it replaced (`linx_before_restore`, `*.before-restore`) until the next restore, and checks everything it can before changing anything. From the browser it's reachable only as a system admin's confirmed session on an unfinished setup, and the folder or destination name is checked on both sides of the host boundary (`backup.CheckRestoreSource`: a folder must be a plain absolute path, so it can never be read as a restic backend such as `sftp:` or `rclone:`; a destination must already be set up on the host).
- Backup files (step 5) pass through the control plane's transfer folder encrypted and unopened, for the admin who asked only and for an hour (download), or until the restore ends (upload); the upload is unpacked on the host under strict checks (`backup.UnpackRepository`), never by the control plane.
- THREAT_MODEL.md gets rows for: a stolen backup file (useless without the repository password), a compromised remote destination (can read old snapshots, can't reach the live system), a stolen destination-credentials file (reaches that one remote repository only, not the live system, and not any other destination), and the restore (root-run by the host's agent; the browser only asks).

## 8. Build order (one session each)

1. **Core engine, local only:** `internal/backup` (dump + secrets bundle → restic repository, pair-id, restore reversing it), `linx backup`/`linx restore-secrets` CLI, restic added to `linx setup`'s prerequisites. *(done)*
2. **Remote destinations:** SFTP and S3-compatible repository configuration (`linx backup destination add|list|remove`), credentials sealed as host-side files (see §7), the outbound host-safety guard, `linx backup` running against every configured destination in turn (continue on failure). *(done)* Deliberately CLI-only for now: the admin API/database side (step 3) needs to decide how a browser-triggered "back up now" reaches this host-level command (no container has a way to run arbitrary host commands today; likely a polling systemd timer + status table, the same pattern `linx-firewall-sync` already uses, rather than the reverse).
3. **Schedule and admin API:** `pbx_setting`-style backup settings, `GET/PUT /backup-settings`, `GET /backups` (history), `POST /backups` (back up now), the "backup failure" alert wired up. *(done)* `internal/backupschedule` (Service/Store, mirrors `internal/settings`): the schedule (off/daily/weekly/monthly, time of day, day of week/month) lives on `pbx_setting` like every other admin setting; history is its own table, `backup_run` (migration `0024_backup_schedule.sql`). New scopes `backups:read`/`backups:write` (write marked sensitive: it can trigger a backup and, once step 4/5 land, read one — docs/ADMIN.md §7's confirm-it's-you list is deliberately not extended to schedule changes or "back up now" themselves, only to what's not built yet). Webhook catalog gained `backup.completed`/`backup.failed`. The bridge promised in step 2's note: `linx-backup-agent` (new host binary, `cmd/linx-backup-agent`, installed as a systemd timer every 5 minutes by `installer.BackupAgentPlan`, the same pattern as `linx-firewall-sync` but in reverse — here the *host* does the work and reports back, since only a host binary can run `linx backup` at all) polls a hidden CLI subcommand (`linx-control-plane backup pending`, `docker exec`, same trust as `linx user`) for whether a run is due (a pending "back up now" always wins; otherwise the schedule's own cadence, computed against the most recent run so nothing runs twice for the same period), runs `linx backup --json` (new flag: one JSON summary line instead of the human-readable output, and — since this path is unattended — it never prints a newly generated destination password to stdout, only a note on stderr pointing at the root-only file to read it from by hand) and reports the result back (`linx-control-plane backup report`, JSON over stdin), which records history, clears the pending request, and fires/resolves `backup.failure` (warning if some destinations worked, critical if none did). "Confirm it's you" on the sensitive ones and `GET /backups/{id}/download` are pushed to steps 4/5 (below) — deciding how a downloadable backup ever reaches the browser without the control plane touching decrypted secrets is exactly the boundary the pre-launch security review already drew a hard line around, so it deserves its own careful pass rather than a rushed one here (a zip of the local restic repository's own already-encrypted files, still needing the same repository password to open, is the leading candidate — never a decrypted `restic dump`/`restore` stream passing through the control-plane container).
4. **Setup wizard restore screen:** the "Set up fresh or restore" first screen, the restore request, the whole restore done by the host (§4 "As built"). *(done)* Owner decision 2026-09-27: the browser asks and `linx-backup-agent` does it, keys and database together, instead of keys over SSH + database by the control plane. `internal/backupschedule/restore.go` + `internal/store/backuprestore.go` (migration 0025), `GET/POST /backup-restore`, hidden `backup restore-take|restore-failed|restore-done`, `internal/backupagent` restore path, `linx restore` (`cmd/linx/restore.go`, replaces `linx restore-secrets`), `internal/backup/dbrestore.go` (`Postgres`: `Load`/`SchemaVersions`/`Prepare`/`Swap`, tested against a real Postgres), `backup.CheckRestoreSource`/`CheckSnapshot`/`CheckDestinationName` (destination names are now checked when added too), agent timer every minute. Web: `web/src/screens/SetupRestore.tsx` (start choice, form, progress, done). Not built: restoring from a *downloaded* backup file (step 5's download doesn't exist yet; a downloaded repository copied into a folder on the server will restore as a folder), and a restore after setup is finished from the browser (by design; `sudo linx restore` covers it). Not yet run end to end on a real server with restic (each part is tested; the full run is for step 6's demo).
5. **Admin screen:** System → Backups (history, destinations, schedule, "back up now", "download"). **Plus upload for restore (owner decision 2026-09-27):** the setup wizard's restore gains a third source, "A backup file on my computer" — the same file "download" produces (the leading design: a zip of the repository's own, still-encrypted files), uploaded from the browser. The control plane only passes the encrypted bytes into a holding folder it can write but not read back (never opens or decrypts them); linx-backup-agent unpacks and restores it as a folder with the given password, and deletes it after the restore finishes or fails. Same gates as the other sources (system admin, confirm it's you, setup unfinished), plus a size cap (about 2 GB). Download and upload are designed together so the file format is one. *(done)*

   *As built (2026-09-27).* **The file** (`internal/backup/archive.go`): a plain tar (not zip: streams, no central directory) of a local restic repository's `config`, `keys/`, `data/`, `index/`, `snapshots/` under one top folder `linx-backup/` — `locks/` and anything else left out, links and special files refused. Unpacking trusts nothing: only plain files and folders under `linx-backup/` with clean relative names, no file twice, at most 200,000 entries and 2 GB, and it must hold a repository `config`. Checked against real restic 0.18.1 (pack → unpack → `snapshots`/`restore` work, a wrong password is refused). Named `linx-backup-YYYY-MM-DD-HHMM.tar` after its newest backup.
   **Download.** `POST /backup-download` (`backups:write`, "confirm it's you" for a session; one at a time per tenant, `download_in_progress`) → migration `0026_backup_download.sql`'s `backup_download` row → `backup pending` answers `run export` (after a restore, before backups) → linx-backup-agent takes it (`backup export-take`), backs up now (reported as a manual run, so the file holds a current backup; if that fails the file still has the older ones and says how old), runs the new host command `linx backup export --json --out FILE` (`cmd/linx/backupexport.go`: the first `local` destination, or `/var/backups/linx` when none is set up; refuses when backups only go to SFTP/S3 — "nothing here to download"), streams the file into the control plane (`backup export-put ID`, stdin) and reports the outcome with the repository password (`backup export-done`). The control plane keeps the file in its **transfer folder** (compose volume `backup-transfer` at `/var/lib/linx/backup-transfer`, on disk, owned by its own user, mode 0700) and the password sealed with ADR-030's key (row `backup_download:<id>`), both for **one hour**, then a sweep (every 5 minutes) removes them. Only the admin who asked (`requested_by` = the caller) can fetch the file (`GET /backup-download/file`, hand-written: `http.ServeContent`, so a broken download resumes with Range) or its password (`POST /backup-download/password`, "confirm it's you" again, audited `backup.password_shown`); anyone with `backups:read` sees that one exists. The password is the repository's own (the same for every backup file from that folder): showing it is the "show it again" §6 always allowed behind a fresh confirm, and it's the only way an admin who never ran `linx backup` by hand ever learns it (the agent's unattended first run generates it without showing it).
   **Upload.** `PUT /backup-restore/file` (hand-written, `application/octet-stream`, streamed to disk: the generated handler's validation would read it into memory) under exactly the restore's own rules — `restoreAllowed`: a system admin's own session, confirmed, setup unfinished, no restore under way — capped at `backupschedule.MaxUploadSize` (2 GB + 128 MB of tar headers; `upload_too_large` 413 before reading when Content-Length says so); the per-request read/write limits are raised to 2 hours for these two only. It lands in the transfer folder as `upload-<id>.tar` (only the newest upload is kept; unused ones go after 2 hours) and the wizard then sends `POST /backup-restore` with `source: upload`, `location: <upload_id>` (checked: the file must still be there, `upload_missing`). The agent fetches it (`backup upload-read ID` → a private folder under `/var/lib/linx`), runs `linx restore --file FILE` (new: unpacks with the checks above into a private folder, then restores it like a folder), and removes it on both sides (`backup upload-delete ID`) however the restore goes. "Can write but not read back" turned out not to be possible as a file permission (the control plane owns what it writes, so it could always chmod it back); what holds instead: the control plane never opens an upload except to stream it to the agent, never parses or decrypts it, and a control plane that did would gain nothing it doesn't already have — it holds the live database and both keys a backup contains, and briefly the restore password anyway.
   **Screens.** System now has its tab bar (§10 of `docs/ui/ADMIN_SCREENS_PHASE1E.md`), with only **Backups** live; the sidebar's System goes there (`/admin/system/backups`). One page, four cards: *Backups* (what's in one; "Back up automatically": Off / Every day / Every week / Every month, day and time, Save; **Back up now** with "Starts within a minute"), *Download a copy* (make a file → waiting → ready: size, newest backup, until when; **Download file**, **Show its password** in an amber box with Copy and "keep it apart from the file"; failed with its reason and Try again; another admin's file noted), *Where backups go* (each destination's result from the newest run — destinations live on the server with their keys, so the page shows them and the `sudo linx backup destination add` command rather than a form), *History* (when, how, result with the failed destinations' reasons, backup ID). Reporters see it all with the buttons greyed ("Only an admin can change backups"). The wizard's restore form has the third choice with a file picker, size, a 2 GB check, and an upload progress bar (XHR, `web/src/lib/backupFile.ts`) before the restore request. Nginx Proxy Manager's generated steps gained `client_max_body_size 3g` (nginx's default is 1 MB); Caddy, Traefik (Pangolin) and the TLS-passthrough doors have no body limit.
   Also fixed: linx-backup-agent mixed `linx backup`'s stderr (the "a repository password was generated" note on a first run) into the JSON it parses, so the first scheduled backup on a fresh server would never have been reported; stderr now goes to the agent's log.
   Not built: choosing which destination a file is made from (always the first local one); the file needs the local destination, so a server backing up only to SFTP/S3 can't offer a download until a local one is added.
   *Demo fixes (2026-09-27):* the web app sent every PATCH as `application/json` where the API takes `application/merge-patch+json` (every admin edit was refused by a real server; `web/src/api/client.ts` `mergePatch`, and the screenshot fakes now refuse it too); restic 0.16 words "already initialized" differently, so every backup after the first failed (`InitRepo` now asks `restic cat config`); adding a first destination silently stopped backups to `/var/backups/linx` and with them downloads (it's now kept as an explicit `local` destination, and the name is reserved while it's the built-in one); History shows each backup's size (`total_bytes_processed` from restic's summary, per destination, `BackupRunDestination.size`).
6. **Security review + demo.** *(review done 2026-09-27; demo: `docs/DEMO_BACKUP.md`)* Findings and fixes in `docs/THREAT_MODEL.md` "Backup review". The one that changes how restore works: **a backup's database is loaded as a powerless role (`linx_restore_loader`) and accepted only if its structure is exactly what this Linx's migrations build at the backup's version** (`backup.Postgres.Check`, `db.ReferenceScript`), so a backup can only ever bring back data, never code that would run as the database superuser; only then does the superuser take it over. Also: SFTP destination details are checked (`backup.CheckSFTP`), a local destination's path must be a plain absolute path, the agent caps an upload it fetches, and `linx setup` installs restic from Ubuntu's archive (`installer.ResticPlan`; the first draft's "downloaded and checksum-verified" became the same signed-apt trust as nftables).
